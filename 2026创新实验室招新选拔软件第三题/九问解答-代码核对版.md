## 1. 采样率怎么算？预分频和重装载取多少？200 kHz 怎么配？

**结论：公式对；200 kHz 对应 `PSC=0`、`ARR=419`。**

定时器触发 ADC 时，采样率就是 TIM3 更新事件频率：

`f_s = f_TIM / ((PSC+1) × (ARR+1))`

TIM3 挂 APB1。F407 在 168 MHz 下 APB1 预分频 4，PCLK1=42 MHz，定时器时钟再×2，所以 **f_TIM = 84 MHz**（`system_stm32f4xx.c` 中 `PPRE1_DIV4`，系统时钟 168 MHz）。

- `PSC = 0`
- `ARR = 419`
- `f_s = 84 000 000 / (1 × 420) = 200 000 Hz`

任意目标频率（`PSC=0`）：

`ARR = 84 000 000 / f_s − 1`

| 目标 fs | ARR | 说明 |
|---|---|---|
| 100 kHz | 839 | |
| 200 kHz | 419 | Base 默认 |
| 400 kHz | 209 | Scope 默认 |
| 500 kHz | 167 | 两份代码的上限 |
| 1 MHz | 83 | **本工程不可用**（见下） |

**原文需要修正的两点：**

1. **200 kHz 不是 Scope 的默认值。** Scope 默认 400 kSa/s（`app_config.h:37`，`bsp_adc.c:167`）；要 200 kSa/s 得发 `RATE 200000` 或改 `ADC_DEFAULT_FS_HZ`。Base 才是默认 200 kSa/s（`adc.c:215-216`）。
2. **1 MHz 只是数学上算得出 ARR=83，不能真的跑。** 两份代码的 `ADC1_SetSampleRate()` 都把 fs 限制在 50 k~500 kSa/s（Base 是 1 k~500 k，`adc.c:228-229`；Scope 是 50 k~500 k，`bsp_adc.c:65-66`）。而且 1 MHz 时 15 周期转换要 1.286 µs > 1 µs，ADC 根本跟不上。现场要改采样率，用 `RATE 200000` / `RATE 100000` 即可。

> 补充：Base 的 TIM3 是 16 位，`ARR` 超过 65535 会截断；`fs` 低于约 1.28 kHz 时 `ARR=84e6/fs−1` 已放不下。实际验收用不到这么低，但知道有这个边界。

**代码依据**：`adc.c:215-216`（PSC/ARR）、`adc.c:224-243`（SetSampleRate）、`bsp_adc.c:61-79`、`app_config.h:35-40`。

## 2. F407 一次转换多少个 ADCCLK？和 F1 差在哪？ADCCLK 多少？为什么不能更高？

**结论：F407 12 位是 `T_CONV = T_SAM + 12 个 ADCCLK`；F1 是 `T_SAM + 12.5`；本代码 ADCCLK = 84/4 = 21 MHz；上限 36 MHz。这些都对。**

**但“代码配 15 Cycles”要分工程说：**

| 工程 | fs | 采样周期 | 总周期 | 转换时间 | 占采样周期 |
|---|---|---|---|---|---|
| Base | 200 kSa/s | **84** | 96 | **4.57 µs** | 91%（5 µs） |
| Base | ≤40 kSa/s | 480 | 492 | 23.4 µs | 94%（25 µs） |
| Base | >205 kSa/s | 15 | 27 | 1.286 µs | — |
| Scope | 400 kSa/s | 15 | 27 | 1.286 µs | 51%（2.5 µs） |
| Scope | 500 kSa/s | 15 | 27 | 1.286 µs | 64%（2 µs） |

- **Base 在 200 kSa/s 实际用的是 84 cycles，不是 15。** `adc_apply_sample_time()` 的分支是：`fs ≤ 40k → 480`；`fs ≤ 205k → 84`；否则 `15`（`adc.c:126-138`）。所以原文的“27 个 ADCCLK ≈ 1.29 µs”是 15 cycles 的结果，对应 Scope 的 400 kSa/s，或 Base 在 >205 kSa/s 时；不是 Base 在 200 kSa/s 的配置。
- Base 文件头注释还写着“15 + 12 cycles = 1.29 µs < 5 µs”（`adc.c:4-6`），这条注释已经过时，和 `adc_apply_sample_time()` 的实际选择不一致。建议改掉，否则学员一定会问。
- 84 cycles 在 200 kSa/s 下只剩 0.43 µs 余量（4.57 µs vs 5 µs），所以代码在 fs >205 kSa/s 时必须把采样时间缩到 15 cycles，否则转换会挤进下一个触发周期。
- F1 的固定部分确实是 **12.5 个周期**，采样档位也不同（1/7/13/28/41/55/71/239）；F4 是 12 个周期，采样档位 3/15/28/56/84/112/144/480。

**为什么 ADCCLK 不能更高：**

- F407 数据手册规定 ADCCLK 最大 **36 MHz**（典型值 30 MHz；F1 的上限则是 14 MHz）。
- APB2=84 MHz，分频只能取 /2、/4、/6、/8：/2=42 MHz 超限；/4=21 MHz、/6=14 MHz、/8=10.5 MHz 都可用。原文说“只能 Div4=21 或 Div6=14”，漏了 Div8，严格说不完整，但不影响结论。
- 时钟越高，同样的“采样周期数”对应的真实采样窗口越短，采样电容充放电不够，读数偏低；转换器内部比较器也来不及建立。
- **“甚至损坏”这个说法不准确。** 超过 36 MHz 是超规格使用，结果是“不保证、可能乱码/错位”，一般不会把 ADC 烧坏；但绝不能这么设计。

**代码依据**：`adc.c:122-138`（采样时间选择）、`adc.c:162-166`（Div4）、`bsp_adc.c:107-126`（Scope 15 cycles）。

## 3. 采样率和频率分辨率的关系？N=1024、Fs=100 kHz，1 kHz 落在第几个 bin？不落在整数 bin 上会怎样？

**结论：数学推导对；但 N=1024/Fs=100 kHz 是题目说明里的例子，不是当前代码的参数。**

`Δf = f_s / N`；1 kHz 的位置 `k = f / Δf`。

- `Δf = 100 000 / 1024 = 97.656 Hz`
- `k = 1000 / 97.656 = 10.24`
- bin 10 的中心是 976.56 Hz，bin 11 是 1074.22 Hz；1 kHz 落在两者之间，离 bin 10 差 0.24 bin。

**不落在整数 bin 上：**

- 矩形窗下能量会泄漏到相邻 bin，主峰幅值下降、旁瓣抬高；这就是**频谱泄漏**。
- 幅值误差叫**扇贝损失（scalloping loss）**：矩形窗最坏（差 0.5 bin）约 −3.9 dB；本例差 0.24 bin，约 −0.8 dB，也就是峰值读数会偏小约 9%。
- 直接取最大 bin 的频率，可能读到 976.6 Hz（偏低 2.3%），也可能跳到 1074.2 Hz；对 3% 的测频指标很危险。
- 解决办法：加窗（汉宁/汉明）、峰值插值（Jacobsen/Quinn）、整周期采样；或者干脆用过零法测频——Scope 的 `osc_measure.c` 就是过零插值，不依赖 FFT bin。

**当前代码的实际分辨率：**

| 工程 | N | fs | Δf | 1 kHz 的 bin |
|---|---|---|---|---|
| Base | 2048 | 200 kSa/s | 97.66 Hz | 10.24 |
| Scope | 16384 | 400 kSa/s | 24.41 Hz | 40.96 |
| 题目例子 | 1024 | 100 kSa/s | 97.66 Hz | 10.24 |

Base 的 2048@200k 和题目例子 1024@100k 的 Δf 恰好一样，所以“1 kHz 在 10.24 bin”这个结论对 Base 也成立；Scope 则是 40.96 bin，仍然不是整数。

**代码依据**：`osc_measure.c:148-172`（过零测频）、`osc_measure.c:60-86`（Goertzel 单 bin）、`app_config.h:35-40`。

## 4. 波形为什么左右滚动？触发怎么判？触发电平取在哪？为什么不能取峰值附近？

**结论：滚动原因、峰值附近不可取——这两段对。触发算法的描述要按当前代码重写，而且 Base 的自动触发实现有缺陷。**

**为什么滚动：** 自由运行时，每帧 DMA 半区的起点和信号相位没有固定关系；新帧覆盖旧帧后，屏幕上的相位逐帧偏移，看起来就是左右滚动。触发的作用是把每帧的起点锁到波形的同一相位。

**Scope 的触发（当前主工程，`osc_capture.c:82-141`）：**

1. 触发电平默认自动跟随被测直流分量 `Vdc`（`osc_capture.c:404-413`）；发过 `TRIG 1.50` 后改为手动，发 `TRIG AUTO` 恢复自动。
2. 触发搜索带 **3% Vpp 的滞回**（最少 3 LSB，`osc_capture.c:63-70`），防止噪声在电平附近反复触发。
3. 上升沿：先等到 `raw[i-1] + hyst <= level`（armed），再找 `raw[i-1] < level && raw[i] >= level` 的穿越点；下降沿对称。
4. 穿越点在相邻两点之间做**线性插值**，得到亚采样精度的起点。
5. 窗口左边留 **20% 预触发**（`pre = win/5`），所以能看到触发点之前的波形。

**Base 的触发（`adc.c:73-121`）：**

- 手动档：单电平，上升沿 `s[i-1] < level && s[i] >= level`，下降沿对称；这个是对的。
- 自动档：求一帧 min/max，`span<80` 判噪声不触发；`low=min+span/4`、`high=max-span/4`；上升沿条件是 `s[i-1] <= low && s[i] >= high`。
- **这里有一个实现缺陷**：它要求**相邻两个采样点**从 low 以下直接跳到 high 以上。以 1 kHz 正弦、200 kSa/s 为例，每点最多只变几十 LSB（1 Vpp 时约 19 LSB），而 low 到 high 的带宽是 span/2（1 Vpp 时约 620 LSB），永远不可能在一步内跨过去，于是函数返回 0，自动触发对正弦实际失效（手动档正常）。正确写法是加一个 armed 状态：先等 `s[i-1] <= low`，再在后续点上等 `s[i] >= high`，Scope 的 `osc_find_trigger()` 就是这么做的。

**触发电平取在哪：**

- Scope：自动档取 `Vdc`（对称波形就是中值），手动档取 `TRIG` 设定的电压；屏上黄线就是该电平。
- Base：手动档取 `level`；自动档意图是 1/4 和 3/4 双阈值，但受上面的缺陷影响；另外 Base 屏上自动档画的是 `(min+max)/2` 的中值线（`ui.c:148-151`），并不是实际用的 low/high 阈值，看起来会对不上。

**为什么不能取峰值附近：**

- 峰值处斜率接近 0，信号在峰值附近来回抖动，穿越点不稳定，触发位置前后跳。
- 峰值易受噪声和幅度波动影响，容易漏触发或误触发。
- 沿上（50% 幅度附近）斜率最大，穿越快、定位准；再加滞回，才能既稳又抗噪。

**代码依据**：`osc_capture.c:82-141`、`404-421`；`adc.c:73-121`；`ui.c:144-151`。

## 5. 自动/正常/单次三档，无信号时分别表现？单次档怎么重新武装？

**结论：这张表与 Scope 完全一致；但 Base 没有 NORMAL 档。**

**Scope（`osc_capture.c:423-449`）：**

| 档位 | 有触发 | 无信号/无触发 |
|---|---|---|
| AUTO | 对齐更新 | 取最新窗口自由刷新，基线可见，参数继续更新 |
| NORMAL | 对齐更新 | 保持上一帧，不更新参数 |
| SINGLE | 捕获一帧后 `s_run=0` | 保持等待，屏幕停在上一帧 |

**单次档重新武装：**

- 发 `SINGLE` 命令，或按屏幕 `MODE` 按钮把模式切回 SINGLE；最终调用 `OSC_SingleArm()`，把 `s_mode=OSC_MODE_SINGLE`、`s_run=1`（`osc_capture.c:485-490`）。
- 等下一次满足触发条件，捕获一帧后 `s_run=0`，状态栏显示 `HOLD SING`。
- 再发一次 `SINGLE` 就重新武装。

**Base 的实际情况（`cmd.c:117-134`、`298-323`）：**

- 只有 `RUN` / `STOP` / `SINGLE`，**没有 NORMAL**。
- `SINGLE` 只是把 `g_run=1, g_single=1`；主循环里只要有新帧、串口空闲，就把一帧数据发出去，然后 `g_single=0, g_run=0`。它**不检查是否找到触发点**，所以单次捕获到的可能是一帧没对齐的波形。
- 重新武装 = 再发一次 `SINGLE`；`STOP` 是冻结，不是重新武装。

> 如果培训用的是 Base，就不能照原文讲“三档”；如果用的是 Scope，这张表可以直接用。

## 6. 时基档位改的是采样率还是显示窗口？两种差别？垂直档位是改增益还是缩放像素？

**结论：两种实现都存在，但这两套代码选的不是同一种，原文没有说清。**

**Scope：改显示窗口，采样率不变。**

- 采样率由 `RATE` 或 `ADC_DEFAULT_FS_HZ` 决定（默认 400 kSa/s）。
- TB 只改窗口点数：`win = TB × 10 × fs`（10 格横轴，`osc_capture.c:49-60`），再从 16384 点的一帧里取 `win` 点显示。
- 窗口点数 > 屏幕列数时用 min/max 峰值保持；窗口点数 < 屏幕列数时用线性插值折线（`osc_capture.c:146-220`）。
- TB 档位表 10/20/50/100/200/500/1000/2000 µs/div；改采样率时 `OSC_SetSampleRate()` 会自动把当前时基收回到合法档位（`osc_capture.c:643-661`）。

**Base：改采样率，帧长不变。**

- `TB <time>` 里 `fs = ADC_FRAME_LEN × 1e6 / (us × 10)`（`cmd.c:166-183`），`N=2048` 固定，10 格横轴；实际窗口 = N/fs = 10×TB。
- 所以 Base 改 TB 会重配 TIM3 ARR；fs 被夹在 1 k~500 kSa/s，TB 小于约 409.6 µs/div 时会被 500 kSa/s 截断（实际 TB 约 409.6 µs/div，窗口 4.096 ms，不是设定的值）。
- 另外 Base 上电默认 200 kSa/s + TB=1000 µs，理论窗口是 2048/200k=10.24 ms，而屏幕标签按 10 ms 画，差 2.4%；发一次 `TB 1ms` 后 fs 会变成 204.8 kSa/s，才严格对齐。

**两种做法的差别：**

- 改 fs：影响实际采样质量、抗混叠上限（奈奎斯特）和每点时间间隔；需要重配定时器。
- 改窗口：采样率不动，只改“从已采到的一帧里取多少点来显示”；不增加新信息，时间分辨率的根仍然是 fs。
- 现场验收要“改时基”时，Scope 直接 `TB 500us`；Base 要意识到它同时在改采样率。

**垂直档位：两份代码都是软件映射，没有模拟增益。**

- 没有 PGA/可编程增益放大器；ADC 前端固定，VDIV 只改“ADC 码值 → 屏幕 y 坐标”的比例（Scope 还有跟随 Vdc 的垂直偏移）。
- 这**不是**把同一帧位图拉伸：每帧都是新采的数据，只是按新的 V/div 重新映射；所以“切换后波形实际幅度正确变化”是满足的。
- 如果题目要求的是模拟前端增益切换，这块硬件没有，只能在软件上做映射；Scope 的说明文档也是这么写的（`01-代码框架与TODO说明.md:215-218`）。

**代码依据**：`osc_capture.c:49-60`、`146-220`、`541-558`、`596-625`；`cmd.c:166-183`；`adc.c:224-243`。

## 7. DMA 用 Normal 还是 Circular？为什么？半传输/全传输中断各做什么？

**结论：两份代码都用 Circular；HT/TC 是乒乓双缓冲。但“HT 中断里拷前半帧”这个说法不对——中断里只置标志/偏移，拷贝在主循环。**

**为什么 Circular：** 示波器要连续采集，缓冲采满后必须自动回到起点覆盖；Normal 采满即停，需要软件重启 DMA，不适合连续波形。

**Scope（`bsp_adc.c:13-29`）：**

- DMA 缓冲 = 2×16384 个半字 = 64 KB；HT 表示前半满，TC 表示后半满。
- 中断里只做两件事：`s_frame_offset = 0 / ADC_FRAME_LEN`，`s_frame_seq++`；不做拷贝、不做测量。
- 主循环 `ADC1_GetLatestFrame()` 短暂关中断，快照 `seq+offset`，返回指向半区的指针（零拷贝）；然后 `MEAS_Process()`、触发、抽取、绘图都在主循环。
- 半区时间 = 16384/400k = **40.96 ms**，CPU 有充足时间处理。

**Base（`adc.c:14-29`、`39-66`）：**

- DMA 缓冲 = 2×2048 个半字 = 8 KB；HT 置 `offset=0`、`TC` 置 `offset=2048`，并置 `s_frame_ready`。
- 主循环 `ADC1_CopyFrame()` 把半区 2048 点拷到 `s_raw_frame`，再做 3 点中值滤波到 `s_frame`；触发和绘图用滤波后的帧。
- 半区时间 = 2048/200k = **10.24 ms**，拷贝+中值+触发+绘图必须在这之内完成，否则半区会被 DMA 覆盖。

**乒乓的关键：** CPU 处理 A 半区时，DMA 写 B 半区；两边不打架。但前提是“处理一帧的时间 < 半个缓冲区的时间”，否则还是会丢帧。中断本身必须短，重活放主循环。

## 8. 串口指令怎么收？为什么不能在中断里解析？收到一半断了会怎样？

**结论：架构描述对（中断收字节 → 环形缓冲 → 主循环解析）；但“本工程若用查询接收”这句不对——两套工程都是中断+环形缓冲，而且都没有半帧超时。**

**实际实现：**

- **Base**（`usart.c:267-307`）：USART2 RXNE 中断把字节塞进 512 B 环形缓冲；主循环 `CMD_Task()` 取字节、按 `\n` 组行、解析；命令行长 200 字符；超过 200 或环形缓冲溢出 → 回 `ERR` 并丢弃到下一个 `\n`。发送走 DMA1 Stream6（Normal 模式，12 KB 缓冲，115200）。
- **Scope**（`framework/SYSTEM/usart/usart.c`）：USART2 RXNE 中断进 2048 B 接收环；主循环 `CMD_Task()` 每次读最多 32 B，按行解析；行长 256；连续 >200 字节没有换行 → 回一次 `ERR`，丢弃到下一个 `\n`；发送走 8192 B 发送环 + TXE 中断，921600。

**为什么不在中断里解析：**

1. 中断要短：解析可能含字符串比较、浮点、查表，耗时长会阻塞 DMA/ADC 和其他中断；
2. 指令不定长，中断里凑不齐完整帧；
3. 复杂解析出错难定位，影响实时性；
4. 中断被拉长，ADC/DMA 可能丢数据。

**收到一半断了会怎样（这是两份代码共同的短板）：**

- 没有帧超时/IDLE 机制：半截命令会留在 `g_cmd_line` / `s_line` 里，下一帧的字节直接拼上来；到下一个 `\n` 时把拼接后的字符串当命令解析，大概率回 `ERR`，但**原本想发的那条命令已经丢了**。
- 只有“行超过 200 字节”或“环形缓冲溢出”才会强制复位；正常停顿不会复位。
- 正确做法：开 USART IDLE 中断，或用一个 1~2 ms 的软件超时；空闲超时后丢弃不完整帧、复位行指针（可选回 `ERR`），再开始新帧。

**代码依据**：`usart.c:267-307`；`framework/SYSTEM/usart/usart.c:70-100`；`osc_cmd.c:505-544`；`cmd.c:236-281`。

## 9. 屏幕刷新、ADC 采集、触摸扫描、串口收指令各跑在哪个上下文？优先级怎么排？为什么？

**结论：总体划分对；但具体优先级要分工程说，原文写的是 Scope 的排序，不是 Base 的。**

**Scope（`app_main.c:59-66`、`bsp_tick.c:22-26`、`usart.c:62-64`）：**

| 任务 | 上下文 | 优先级/说明 |
|---|---|---|
| ADC 转换 + DMA 搬运 | TIM3/ADC/DMA 硬件 | 硬件自动，不占 CPU |
| DMA2 Stream0 HT/TC | 中断 | 抢占 **1**（最高）；只置偏移/序号 |
| 串口收/发字节 | USART2 中断 | 抢占 **2**；RX 进环，TXE 出环 |
| 1 ms 节拍 | TIM6 中断 | 抢占 **3**；只累加 `s_tick_ms` |
| 测量/触发/抽取 | 主循环 `OSC_Task` | 最低；浮点、Goertzel、触发搜索 |
| 触摸扫描 | 主循环 `UI_Task` | 每 10 ms 扫一次（`osc_ui.c:701-704`） |
| 屏幕刷新 | 主循环 `UI_Task` | 45 ms 限速重绘（约 22 FPS） |
| 指令解析 | 主循环 `CMD_Task` | 最低；按行解析 |
| VOFA 发送 | 主循环 `VOFA_Service` | 有空间才发，不阻塞 |

**Base（`adc.c:202-206`、`usart.c:189/222`、`main.c:20-24`）：**

| 任务 | 上下文 | 优先级/说明 |
|---|---|---|
| ADC + DMA | 硬件 + DMA2 Stream0 中断 | 抢占 **1** |
| 串口发送完成 | DMA1 Stream6 中断 | 抢占 **2** |
| 串口接收 | USART2 中断 | 抢占 **3**（比 TX DMA 低） |
| 指令解析 | 主循环 `CMD_Task` | 最低 |
| 触摸扫描 + 屏幕刷新 | 主循环 `UI_Task` | 最低；全屏重绘后 `delay_ms(20)` |

**排序理由：**

- 实时性：采样 > 通信 > 人机交互；
- 中断里只做最短动作（搬数据、置标志），重活放主循环；
- 屏幕刷新最慢、最占 CPU，放主循环不会影响采集和通信；
- 触摸是人操作，毫秒级延迟可以接受。

**原文需要修正：**

- “串口 RX 次之”只对 Scope（USART2=2）；Base 的 RX 是 3，比 UART TX DMA（2）还低。
- 原文没提 Scope 的 TIM6 1 ms 节拍（3）和 Base 的 UART TX DMA（2）。
- “屏幕刷新最慢且可重入”措辞不对：显示代码不是可重入的，只是允许被中断打断、允许延后。

## 附录 B：Base 工程的额外问题（如果还要拿它演示）

1. **文件头注释过时**：`adc.c:4-6` 还写着 15+12=1.29 µs，但 200 kSa/s 时 `adc_apply_sample_time()` 选的是 84 cycles。改注释或改成打印实际采样时间。
2. **自动触发对正弦失效**：`ADC1_TriggerIndex()` 自动档要求相邻两点跨过整个 1/4~3/4 带（`adc.c:109-118`）；1 kHz 正弦每点只变几十 LSB，永远不满足，返回 0。手动档正常。可参考 Scope 的 `osc_find_trigger()` 改成 armed + 单电平 + 滞回。
3. **测频算法有问题**：`measure.c:39-54` 同样要求单点跨过 `mid±10%` 带，1 kHz 正弦会得到 `cross=0`、F=0；方波能跨过，但 `f=(cross-1)/(2×duration)` 多除了 2，1 kHz 方波会显示 500 Hz。Scope 的 `osc_measure.c` 已用 armed 过零 + 插值 + 正确公式，建议直接替换。
4. **PA1 的板级风险**：Base 用 PA1/IN1；如果板子是冠军407，PA1 是 LAN8720 的 RMII_REF_CLK，不是模拟输入（Scope 已改 PA5/IN5，见 `app_config.h:16-22` 和 `01-代码框架与TODO说明.md:116-118`）。用 Base 前先确认板子和飞线。
5. **低采样率边界**：Base 的 `ADC1_SetSampleRate()` 下限写 1 kHz，但 TIM3 是 16 位，`ARR=84e6/1k−1=83999` 放不下，会被截断；实际低于约 1.28 kHz 就不准了。

> 结论：Base 适合讲“TIM3 触发 + DMA + 双缓冲”的最小链路；一旦要讲触发对齐、三档模式、测频，建议直接用 Scope 框架，Base 只作为过渡。
